Execution time index

The geometric mean of every module’s time against its own first measurement, so 100 is where the window started and 104 is four percent slower. The typical module: alphafold3 at 1.6 s counts exactly as much as detr at 1.4 ms. Lower is faster.

Total module time

The same runs, summed instead of averaged — what the whole suite costs, and therefore mostly what the three heavy modules cost (alphafold3, stable diffusion 1.5, sdxl). Read beside the index, not instead of it: a run can move here and not there, which says one big module moved and nothing else did. A run that did not measure the whole suite reports no total at all rather than a smaller one.

Where the time goes

Total milliseconds per run, split by model category. One panel per stack, all on one scale so the panels can be read against each other.

What moved

Every module whose time changed from the previous run by more than that stack’s noise floor, newest run first, the largest three named per stack. A module is replayed in isolation and timed once per run, so the floor is the only evidence of what a quiet night looks like: it is the 90th percentile of all run-to-run changes, which means roughly one module in ten clears it on a night when nothing happened. Treat a row near the floor as weather and a row far above it as news.

All three stacks run the same modules against the same openxla/xla commit, so every stack on a row means they all moved the same way at once — the thing they share is the XLA commit. this stack only means the others measured the module and held still, which points at the ROCm stack rather than at XLA, and is the row worth chasing. vs start is the other half of the story: a module that comes straight back the next night was a blip, one that stays put is a regression.

HIP request latency

rocm_latency_check_tool, which times a H2D → busy-kernel → D2D → busy-kernel → D2H round trip against a fixed-duration GPU kernel. The compute is deliberately constant, so what moves here is HIP runtime and copy overhead, not kernel selection. Colour is the stack, dash is the GPU count.

Each figure is one 10-second run per GPU count. The median holds steady; the p99 is a handful of requests and a single stall moves it by an order of magnitude, so read it as a count of stalls rather than as latency. The nightly runs this tool on the newest stack only — the figure characterises the ROCm runtime rather than the XLA tree, so re-measuring it on the release stacks would only re-measure the same interconnect — which is why the other stacks’ lines stop where that changed rather than running on.
