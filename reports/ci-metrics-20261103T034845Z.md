### Where the time to signal goes (ROCm on DO, NV on Google runners)

For each commit, the lane's job that finishes last is followed from the moment the SHA was first triggered. Every second lands in exactly one named phase, and each row adds up to its total (checked in code), so there is no unaccounted time. One row per lane, over all hours of the window.

openxla/xla runs more than one job family in a single workflow, so its lanes get one row per family. Both rows cover the same commits, so they share one **n**; **Total** is that family's own signal and **Lane signal** is the combined one the PR actually waits for - the slower family on each commit, which is why it repeats down a lane. The count beside the family name is how often it was the family that finished last.

## The ask: more runners

| Pool | What it does today | What we need | What it unblocks |
| --- | --- | --- | --- |
| DO | Builds and launches every ROCm presubmit job | *pending (owner: user)* | Removes the provisioning wait paid on every job, and the multi-GPU starvation |
| RBE | Runs the bazel test actions dispatched from DO | *pending (owner: user)* | Shortens test execution, the largest phase of time to signal |
| Remote build | JAX: nothing. `rocm_rbe_dynamic` sets `--spawn_strategy=local`, so compile actions run on the GPU runner | *pending (owner: user)* | Stops GPU nodes being used as build machines, freeing the same hardware for tests without buying more |

> Google's CUDA presubmit compiles remotely (`--spawn_strategy=remote,worker,standalone,local`, seen in this window's logs); JAX ROCm pins builds to the GPU box, while `openxla/xla` ROCm already uses `--spawn_strategy=dynamic`.

**openxla/xla:** the (XLA jobs) runs 551 ROCm targets against NV's 613, and the (JAX jobs) runs 143 ROCm targets against NV's 154.

**jax-ml/jax:** the presubmit runs 143 ROCm targets against NV's 150.

**Gating coverage:** with more hardware we can pitch Google to gate PRs on far more ROCm tests than the single target we gate on today.
