Where the time to signal goes ROCm on DO, NV on Google runners

For each commit, the lane's job that finishes last is followed from the moment the SHA was first triggered. Every second lands in exactly one named phase, and each row adds up to its total (checked in code), so there is no unaccounted time. One row per lane, over all hours of the window.

The ↳ rows under an OPENXLA lane break it into its two job families: openxla/xla runs its own tests and the JAX integration tests in one workflow, so the lane row is whichever family finishes last on each commit. The two ↳ rows cover the same commits as the lane row above them, so all three share one n; set the signal counts the commits where that family was the one that finished last. A family that set the signal on every commit has the same figures as its lane row, because on those commits it is the lane.

Superseded runs + re-run delay = time from the SHA's first trigger to the start of the run that finally signalled. Waiting on earlier jobs = needs: jobs ahead of the lane's last job in the same run. Runner teardown + completion report = job wall time minus the sum of its step durations; almost all of it sits after the Complete job step, before GitHub marks the job done, so the check stays pending while the ephemeral runner shuts down.
